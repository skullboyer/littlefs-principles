HOW TO READ THIS ANALYSIS

源码行为、设备前提与执行快照

本文按仓库内 littlefs 2.11.3 的 lfs.c、lfs.h、SPEC.md 和 README.md 拆解。动画中的算法步骤对应源码控制流；具体块号只在标为固定快照或明确输入时成立。

源码定义的行为

函数调用顺序、tag/CTZ 结构、CRC 边界、分配扫描与恢复分支以源码和磁盘格式规范为准。文中链接直接指向对应函数。

保证成立的前提

掉电一致性依赖 read/prog/erase/sync 遵守 lfs_config 契约。若设备有写缓存，sync 必须真正刷新；设备报告错误也必须准确。

固定执行快照

页面通过仓库 lfs.c 2.11.3 在 RAM 块设备上执行 format/mount/create/write/sync/append，并读取块内容核对。block 0/1/10/11/12 只属于这组配置。

参数化源码路径

覆盖、目录 split、allocator 和 pair 重定位动画展示源码在指定输入下的控制流，不把符号块号说成实测地址；每个动画聚焦一条路径，不代表全部代码分支覆盖。

保证边界：littlefs 的文件系统操作具有掉电一致性设计；文件数据更新以 lfs_file_sync / close 提交。发生断电时，尚未确认成功的调用可能已留下可恢复的新提交，也可能仍恢复旧提交；应用应以重挂载后的状态和 API 返回值为准。快照执行使用内存块设备：erase 写入 0xff、prog 按配置对齐、sync 成功返回且无设备写缓存；它验证 littlefs 的实际分配和磁盘编码，不构成物理 Flash 的掉电测试。CRC 用于识别有效提交，不是任意介质损坏的修复机制。见 README 的 sync 契约 与 SPEC 元数据提交格式。
01 / SYSTEM MODEL

从 API 到 Flash：五层职责

littlefs 不直接认识 SPI NOR、EEPROM 或模拟磁盘。它只要求底层提供按块读取、编程、擦除和同步的回调；块大小与写入对齐规则由配置描述。

01 · APPLICATION

应用与文件 API

调用 mount、open、read、write、sync、rename 等接口，并分配运行时对象。

02 · CORE

lfs.c / lfs.h

路径解析、目录操作、文件缓存、错误传播和事务组织。

03 · METADATA

Metadata pairs

双块、追加式的小日志；记录名称、大小、CTZ 指针和全局状态。

04 · DATA / ALLOC

COW + allocator

CTZ 块链承载文件内容；lookahead allocator 搜索可用块。

05 · BLOCK DEVICE

Flash / device

read、prog、erase、sync；物理介质约束通过 lfs_config 传入。

可靠性边界： littlefs 能处理块设备操作中断并从最后一个有效提交恢复，但底层驱动仍须遵守编程/擦除约束；若设备缓存写入，sync 必须把写入真正推到持久介质。
02 / ON-DISK MAP

逻辑块不是文件的固定地址

littlefs 把设备抽象成等大的逻辑块。每个目录 metadata pair、文件 CTZ 节点都从块池动态分配；除了格式化起点等引导约定，应用不应依赖某个文件落在固定块号。

03 / FORMAT & MOUNT

format 建立引导点，mount 重建运行时状态

磁盘没有一张完整目录索引或已分配块清单。mount 依据元数据日志恢复根入口和全局状态；需要找空闲块时，再遍历可达数据并填充 lookahead。

01 / BOOT PAIR找到有效 root metadata

format 初始化根 pair 并写入 littlefs superblock 标记和版本、块大小、容量限制等字段。

02 / FETCH校验提交与版本

mount 读取 pair 的 revision、entries 和 CRC，检查 littlefs 标识、磁盘版本及配置兼容性。

03 / GLOBALS汇总 move / sync 状态

沿 metadata tail 线程发现全局 delta，恢复进行中的 rename 或目录链修复标志。

04 / LAZY ALLOC准备缓存与扫描器

mount 初始化 allocator 状态，但不会把整个块设备的分配 bitmap 长期保存在 RAM。

format 会改写介质：它不是 mount 的自动补救动作。superblock 保存磁盘格式版本及几何/限制信息；主版本不兼容或设备参数不匹配时，mount 应报错并由应用决定下一步。
04 / DESIGN GOALS

三个约束，导出一套混合结构

单靠原地更新、纯日志或整棵树复制，都很难同时满足掉电安全、写入寿命和固定 RAM。

核心组合：局部日志负责原子性，COW 数据结构负责容量与写入效率。

元数据变更被限制在双块 metadata pair 中；文件数据采用不可变块，更新时新建块，再提交新引用。小日志和 COW 相互补位。

GOAL A

任意时刻掉电可恢复

数据块先写，元数据后切换引用。元数据提交带 CRC，未完成的尾部提交不会被当成最新状态。

GOAL B

避免固定热点

数据块按需动态分配；metadata pair 会轮换块。磨损控制以统计分散为主，不维护精确的全盘擦除计数。

GOAL C

RAM 有上界

不把整个目录树或分配表常驻内存。用户提供有限的文件缓存与 lookahead 缓冲区。

TRADE-OFF

空间、延迟和扫描

元数据查找可能遍历目录链；首次分配可能扫描块；COW 会暂时保留新旧版本占用的空间。

05 / ATOMIC METADATA

Metadata pair：两块组成一个可轮换的小日志

每个 pair 保存两个块地址。当前块追加提交，空间不足时把仍有效的条目压缩到另一个块；只有完整 CRC 才会让新快照成为有效状态。

06 / COPY-ON-WRITE FILE DATA

CTZ skip-list：倒向链接，跳过中间块

大文件由不可变数据块组成。每个新块保存数据和若干指向较早块的指针；指针层数由块序号的 trailing-zero 特性决定，支持较快定位，又无需常驻整张索引表。

CTZ 字段按源码展开：索引为 i 的非首块实际包含 ctz(i)+1 个 32-bit back pointers，随后是文件数据；指针层级和容量由 lfs_ctz_index 计算。上方角色图不赋予这些节点真实物理块号。参见 lfs_ctz_index、lfs_ctz_find 与 SPEC CTZ structures。
小文件的例外路径inline data

当文件内容能够放进目录 metadata pair 的可用空间时，littlefs 可以把内容以内联结构存进目录项。它避免额外数据块，但受到目录块容量约束；文件变大后会转换为 CTZ 结构。

目录记录是索引入口：目录保存名称、类型、大小和文件数据结构的描述。大文件正文不塞进目录日志，而放在 CTZ 数据块中。
CTZ 节点的头部、容量和定位32-bit block pointers
block index i > 0: [pointer 0][pointer 1] ... [pointer ctz(i)][file payload ...] pointer count = ctz(i) + 1 payload bytes = block_size - 4 × pointer_count

第一块没有回溯指针；后续块先放指针，再放正文。平均每个块约两个 32-bit 指针的额外空间。littlefs 使用 32-bit block address，设计推导出的最小 block_size 为 104 bytes。

CTZSTRUCT metadata: head = 最后一块的 block address size = 文件总字节数 read(pos): 1. 由 size / block_size 推导候选索引 2. 用 popcount 修正指针头部带来的偏移 3. 从 head 选不越过目标的最大 skip 4. 重复跳转直到 target block

文件项只需保存 head 和 size。lfs_ctz_index 计算块索引/偏移，lfs_ctz_find 沿 skip pointers 找目标块。

更新位置影响写放大：追加时，未满的旧尾块会被复制到新分配块；中段覆盖时，littlefs 从目标位置建立新写分支，再从旧文件读取并重放未改动的后缀。新分配块数量取决于目标偏移、旧文件大小、写入长度与 block_size；源文件链在新 CTZSTRUCT 提交前仍保留。

CRC 用于识别完整 metadata commit；它不是文件正文 ECC。设备 sync 的持久化语义很重要：若 CRC 字节已编程但驱动 sync 未返回，掉电后是旧还是新版本取决于设备实际保留了哪些字节，因此阶段 5 标为不确定。

09 / DIRECTORIES & OPERATIONS
目录、路径与跨目录 rename
littlefs 的目录不是一张常驻 RAM 的全局表。每个目录是一条 metadata pair 链；hard-tail 连接同一目录的 pair，soft-tail 把目录 pair 链接入全局遍历链。superblock 记录沿这条链保留，链尾同时承担根目录职责，并非独立的固定分区。

10 / ALLOCATION & WEAR
有界分配器，动态复用块
要分配一个新块，littlefs 需要知道哪些块仍可达、哪些块可复用，却不能把整盘 bitmap 永久留在 RAM。它用固定大小 lookahead 窗口分段扫描。



 
01 / TRAVERSE遍历文件系统引用，识别已占用块；结果用于填充当前扫描窗口。

 
02 / LOOKAHEAD固定大小 bitmap 记录一段块范围，窗口耗尽后继续扫描。

 
03 / ALLOCATE从可用动态块中取新块；数据通过 COW 写入，不覆写仍被引用的数据。

 
04 / RECYCLE旧版本不再可达后，块进入未来的可用空间，可被后续写入重用。


磨损均衡的边界：littlefs 主要做动态磨损均衡：分散新分配和 metadata pair 的擦除机会，并用随机化减少总从低地址开始扫描造成的偏置。它不持续搬迁长期不变的静态数据，也不精确记录每块擦除次数。block_cycles 是 metadata pair 轮换策略的重要参数，不是“每块擦除次数计数器”。


可检测的坏块best effort
底层 prog 或 erase 若能确认某块损坏，可以返回 LFS_ERR_CORRUPT。littlefs 可尝试绕开并重新分配；具体恢复能力仍取决于剩余空间、损坏位置和块设备实现。
检查点与缓存bounded RAM
lookahead 只覆盖有限窗口，file cache 与 read/prog cache 也由配置约束。内存占用不会随文件总数或卷容量线性增长；代价是查找、遍历和重新扫描会增加 I/O。

这条动画固定展示 lfs_ctz_extend 中 erase 返回 LFS_ERR_CORRUPT 后跳到 relocate 标签、清空 program cache 并重新分配的路径。prog/readback 出错有各自调用点和返回条件；其他 I/O 错误不会自动视为坏块。littlefs 不提供持久坏块表，失败块的永久隔离取决于底层设备/驱动。




不持久化空闲表
块是否可用由“当前文件系统能否从根引用到它”决定。删除文件只移除目录引用，旧数据块自然变成不可达块；后续分配扫描确认它不可达，再由写入路径擦除并复用，避免维护一份掉电时也可能失真的 free list。
lookahead 是扫描窗口
每字节 bitmap 表示 8 个块。窗口填充时遍历目录、CTZ 和 pair 引用并标记已占用块；用完后把起点向前移动并继续。完整覆盖的最坏情况可达 O(n²) 遍历；实际通常一两轮就能找到可用块。增大 lookahead 可减少重扫，代价是 RAM。
mount 种子来自介质
挂载遍历 metadata commit 时，把各 commit 的 CRC32 继续累积混合成 seed，再按 block_count 取模。介质没变化时种子可能不变；文件系统变化后起点随之改变，降低设备每次重启都从低地址开始分配的偏置。


坏块能力的边界：块设备层仍需实现正确的读回、ECC 或错误报告；littlefs 可在编程/擦除失败时尝试为当前写入换块重试，但它不是介质修复工具，也不提供通用 ECC 或持久坏块表。lfs_fs_gc 可主动压缩达到阈值的 metadata pair 并预填 allocator 窗口，不会把所有文件数据搬来搬去做静态磨损均衡。

11 / RAM OBJECTS & CONFIG
运行时对象与配置决定内存轮廓
littlefs 的对象和缓存可以由调用方分配。启用静态缓冲区后，文件系统可以避免依赖动态内存分配器。



 
lfs_t已挂载文件系统状态、配置引用、allocator lookahead 状态以及少量全局状态。

 
lfs_file_t / lfs_dir_t每个打开文件或目录由应用持有对应对象；对象数量由应用的并发打开数决定。

 
lfs_config设备回调和几何信息；可选提供 read_buffer、prog_buffer、lookahead_buffer 等静态缓冲区。




几何参数需要与真实设备一致lfs_config
read_size / prog_size底层读取和编程的最小对齐粒度。
block_size / block_count逻辑擦除块的大小与数量；容量约为两者乘积。
cache_size / lookahead_size工作缓存与分配扫描窗口；增大可能减少 I/O 或重扫，也会增加 RAM。
驱动必须守约：prog 只能在已擦除区域按设备规则编程；erase 按整块执行；read 返回的数据必须来自设备状态；有写缓存时 sync 必须刷新。错误码会从 block callback 向上层传播。

打开对象会挂到 lfs_t 的 mlist，用于文件句柄同步和目录/文件移动后的状态修正。调用方必须保证对象和配置缓冲区在使用期间仍然有效；线程并发访问需按构建选项提供锁回调或由应用串行化。

13 / APPLICATION FLOW
应用接入的典型生命周期
先提供块设备和几何参数，再 mount；仅在确认介质为空或明确允许清除时 format。成功写文件后检查 write、sync/close 和 unmount 的错误返回。



常见操作分别提交哪些结构logical changes
操作主要变更掉电后如何收敛


open + create父目录 pair 添加 CREATE、NAME 和空文件结构。目录 commit CRC 有效则文件存在，否则创建回退。


write + sync/close先 flush 文件数据块；再更新 inline 或 CTZSTRUCT（head + size）。非 inline 数据在目录入口提交前先 sync block device。新数据已写而目录未提交时旧入口继续有效；新 metadata CRC 完成后切换到新版本。


truncate / 覆盖更新文件长度及数据结构，旧 CTZ 后缀不再被引用。新旧块通过提交入口区分；旧块成为以后可回收的空间。


remove父目录写 DELETE/删除语义，文件数据不要求同步擦除。完整目录 commit 后名字消失，数据块随不可达而变成候选空闲块。


rename同 pair 可合并更新；跨 pair 通过 global move state 协调源和目标提交。复位 mount 根据 move state 删除源引用并完成移动。

执行操作使用文件、目录、属性 API；处理所有负错误码。
提交写入lfs_file_sync 或成功 lfs_file_close 结束文件更新。

最小写入调用骨架错误检查 + sync boundary
int err = lfs_mount(&lfs, &cfg);
if (err == 0) {
    lfs_file_t file;
    err = lfs_file_open(&lfs, &file, "/cfg/device.ini", LFS_O_WRONLY | LFS_O_CREAT | LFS_O_APPEND);
    if (err == 0) {
        static const char data[] = "sample = 1\n";
        lfs_ssize_t n = lfs_file_write(&lfs, &file, data, sizeof(data) - 1);
        if (n < 0) {
            err = (int)n;
        } else if ((lfs_size_t)n != sizeof(data) - 1) {
            err = LFS_ERR_IO;
        }

        int sync_err = lfs_file_sync(&lfs, &file);
        if (err == 0) err = sync_err;
        int close_err = lfs_file_close(&lfs, &file);
        if (err == 0) err = close_err;
    }

    int unmount_err = lfs_unmount(&lfs);
    if (err == 0) err = unmount_err;
}
介质初始化：这里假定介质已经格式化。首次创建文件系统时，应用确认介质为空或允许清除后才调用 lfs_format，格式化成功再 mount。设备回调的完整配置示例见 中文接入指南。



按代码顺序理解每一步mount → open → write → sync → close → unmount

 
01 / MOUNT恢复已有文件系统
lfs_mount 用 cfg 的块设备回调读取 superblock 和目录状态。只有返回 0 才继续访问；此示例不会因挂载失败就自动 format。

 
02 / OPEN打开或创建目标文件
WRONLY | CREAT | APPEND 表示只写、文件不存在时创建，并从文件末尾追加。CREAT 不会创建父目录，因此 /cfg 必须已存在。

 
03 / WRITE写入正文并检查长度
sizeof(data) - 1 排除 C 字符串末尾的 NUL。负数是 littlefs 错误码；正数还要与预期长度比较，确认整段写完。

 
04 / SYNC显式提交文件更新
lfs_file_sync 刷新文件数据缓存，再提交 inline 内容或 CTZ head/size 元数据；成功返回是本例确认更新持久化的边界。即使已有写入错误，代码仍尝试 sync，但只在 err == 0 时采纳 sync 错误，以保留先发生的错误。

 
05 / CLOSE结束并释放文件句柄
lfs_file_close 会完成必要的最终同步并解除文件对象关联。代码只在没有更早错误时才把 close 错误记为最终错误。

 
06 / UNMOUNT结束文件系统使用
lfs_unmount 释放挂载期资源。示例保留最先发生的错误；如果前面都成功，才返回 unmount 的错误。


调用前提：这段骨架假设 lfs 与 cfg 已初始化、设备回调可用，并且目录 /cfg 已创建。真实应用应按项目策略区分空白介质、配置不匹配和 I/O 故障，再决定是否格式化。



写入中断点速查recovery matrix
掉电位置磁盘可能状态重启后可见结果
新数据块编程中旧目录 commit 完整；新块可能部分写入。使用旧文件版本；损坏/未引用块以后由扫描和重新擦除处理。
数据完成，目录 tag/CRC 未完成旧 commit 完整，新 commit 不完整。忽略无效尾部，使用旧 CTZ head。
目录 CRC 已完整提交，设备同步成功新入口已持久化。使用新 CTZ head 和 size。
metadata pair 压缩时旧块仍可读，目标块可能为空、部分写入或新 CRC 已完整。根据 pair revision 和有效 CRC 选择旧或新快照。
跨目录移动中目标引用和 move state 可能已提交，源引用尚未删除。mount 识别 move state 并按规则完成源侧删除。



新介质格式化：挂载失败不一定代表“空盘”，也可能是配置不匹配、I/O 错误或数据损坏。不要在每次 mount 失败时自动 format，否则可能覆盖可恢复的数据。






14 / PERFORMANCE GUIDE
把 littlefs 用得更顺：从调用模式到参数
littlefs 的性能由块设备延迟、编程粒度、metadata 工作量、缓存配置和应用写入模式共同决定。先减少无效小操作，再用 bench 和目标硬件数据调整参数。



 
01 / BATCH WRITES
把相关数据合并成较大的顺序写入，避免每几个字节就 sync/close。需要掉电持久性的边界再显式 sync。

 
02 / SEQUENTIAL ACCESS
CTZ 追加适合顺序写；频繁随机覆盖会复制被修改位置之后的尾链，设计日志/记录格式时尽量采用追加或分段文件。

 
03 / CACHE GEOMETRY
让 cache_size 与 read_size、prog_size 和 block_size 对齐。增大 cache 可聚合设备调用，但每个打开文件也要预留文件 cache。

 
04 / DIRECTORY SHAPE
把高频查找的文件分布到合适的子目录，避免单个目录增长成很长的 metadata pair 链。

 
05 / FREE SPACE
保留可分配块空间。接近满盘时 allocator 扫描和 COW 更新都更容易遇到高延迟或 NOSPC。

 
06 / MEASURE
仓库提供 make bench、make perf、size/stack 分析目标；在目标存储和真实配置上测量，不用 PC 模拟结果代替 Flash 指标。


同步含义：littlefs 的文件 sync 负责按正确顺序提交文件数据与目录元数据；块设备 sync 负责驱动缓存的持久化。应用的持久化保证同时依赖这两层语义。
